# 决策记录：阶段 A 采用「本地 SQLite + Python CLI」架构

- **日期**：2026-08-10
- **状态**：已批准
- **参与人**：用户、AI 智能体（Codex /root）

## 背景与问题
市、区、街镇、村信息不对称，测试效率低，重复工程多，回传信息收集繁琐。领导常需按特定范围（如某镇、某类设备、风险村）查询装备情况，目前靠人工翻阅多个表格汇总。

## 决策选项与对比

### 方案 A：本地 SQLite 数据库 + Python 查询/导出工具
- **优点**：零部署成本、见效最快；数据库比 Excel 更利于查询与增量更新；后续可直接作为外部 AI 的数据层
- **缺点**：需要命令行操作，暂时没有图形界面

### 方案 B：内网 Web 页面
- **优点**：领导与区域负责人可直接查询
- **缺点**：需要部署环境与账号体系，涉密数据安全评估复杂，见效慢

### 方案 C：直接维护 Excel 宏/脚本
- **优点**：贴近现有习惯
- **缺点**：多 Sheet 查询与状态更新困难，容易出错，不利于后续扩展

## 最终决策与技术考量
采用**方案 A**：Python 3.12 + SQLite（`data/equipment.db`）+ openpyxl 导入导出。
- 数据库 Schema 预留测试状态字段（状态、测试日期、故障描述、维修状态），为阶段 B 做准备
- 使用单位路径按「机构大类/区/街镇/单位」结构化解析，村民委员会统一归一化为村委会，保留原始路径用于追溯
- 预留 `unit_tags` 表支持风险村等标签，满足“风险村设备是否正常”类查询
- 涉密数据（联系人、电话）不录入，导出文件由用户自行保管

## 影响评估
- **部署/运行变化**：本地命令行运行，无外部依赖
- **代码结构变化**：新增 `equipment/` 包（normalize、db、ingest、cli），后续阶段在现有 Schema 上扩展
